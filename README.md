# Quran I3rab AI (V2.1)

API محلي لتحليل **إعراب** القرآن الكريم، مبني على قاعدة بيانات صرفية-نحوية
مرجعية (مشتقة من [The Quranic Arabic Corpus](https://corpus.quran.com))
+ محرك قواعد يحوّل العلاقات الإعرابية إلى جمل عربية مفهومة.

## ⚠️ ما هذا المشروع فعليًا (ولا تسمِّه ما ليس هو)

هذا **ليس نموذج ذكاء اصطناعي مُدرَّب (LLM)**. هو نظامان:

1. **قاعدة بيانات مرجعية** (`quran_i3rab.db`) تحوي تحليلًا صرفيًا ونحويًا
   موثَّقًا لكل كلمة في القرآن (~139 ألف مقطع صرفي لأكثر من 77 ألف كلمة).
2. **محرك قواعد (rule engine)** في `app.py` يحوّل هذه البيانات إلى شرح
   عربي مقروء.

هذا تصميم **متعمَّد وأفضل من الادعاء الزائف**: أي نظام يعتمد فقط على نموذج
لغوي حر لتوليد إعراب القرآن معرَّض لاختلاق إعراب غير صحيح (hallucination)،
وهو خطر خاص عند التعامل مع النص القرآني. الأساس هنا بيانات مرجعية محكّمة
بحثيًا، لا تخمين. لجعله "متكاملًا" بمعنى فهم أسئلة حرة بلغة طبيعية، الخطوة
التالية (موضحة أدناه) هي **إضافة LLM فوق هذه الطبقة**، مقيَّدًا بأن يستشهد
بالبيانات المرجعية لا أن يخترع.

### تغطية محرك القواعد الحالية

البيانات الخام تحوي نحو **120 نوعًا** من العلاقات الإعرابية (فاعل، مفعول
به، خبر إن، جواب الشرط، صلة الموصول، ...). محرك القواعد الحالي (`app.py`)
يقدّم صياغة عربية تفصيلية جاهزة لأكثر الأنواع شيوعًا (~25 نوعًا: فاعل،
مفعول به، مبتدأ وخبر، أخوات كان وإنّ، مضاف إليه، صفة، بدل، حال، معطوف،
تمييز، مفعول مطلق، منادى، ...). لبقية الأنواع (النادرة أو المعقدة نحويًا)
يعرض النظام العلاقة والحالة الإعرابية **كما وردت في البيانات المرجعية**
مع الإفصاح صراحة أن القالب اللغوي التفصيلي لم يُبنَ بعد لهذا النوع تحديدًا
— بدل اختلاق شرح قد يكون خاطئًا. هذا يطابق مبدأ رقم 6 في
`LLM_SYSTEM_PROMPT_AR.txt`: إذا لم توجد معلومة كافية، صرّح بذلك بدل التخمين.

## المكوّنات

| الملف | الوظيفة |
|---|---|
| `quran_i3rab.db` | قاعدة بيانات SQLite: نص الآيات + تحليل صرفي/نحوي لكل مقطع كلمة (مبنية على بيانات Quranic Arabic Corpus). |
| `app.py` | خادم FastAPI: يجمّع مقاطع كل كلمة، ويحوّلها إلى إعراب مقروء عبر محرك القواعد. |
| `LLM_SYSTEM_PROMPT_AR.txt` | توجيه (system prompt) جاهز لربط نموذج لغوي فوق هذا الـ API لاحقًا. |
| `DATA_LICENSE.md` | مصدر البيانات وشروط استخدامها (GPL). |
| `LICENSE` | ترخيص كود المشروع. |

## التشغيل محليًا

```bash
python -m venv .venv && source .venv/bin/activate   # اختياري لكن يُنصح به
pip install -r requirements.txt
uvicorn app:app --host 0.0.0.0 --port 8000
# أو ببساطة:
bash run.sh
```

بعدها افتح التوثيق التفاعلي على: `http://localhost:8000/docs`

## نقاط الوصول (Endpoints)

### `GET /health`
فحص حالة الخادم وتوفر قاعدة البيانات.

### `GET /ayah/{surah}/{ayah}`
تحليل إعراب آية كاملة. مثال: `GET /ayah/1/1`

```json
{
  "surah": 1,
  "ayah": 1,
  "text": "بِسْمِ ٱللَّهِ ٱلرَّحْمَٰنِ ٱلرَّحِيمِ",
  "analysis": [
    {
      "word": "بِسْمِ",
      "pos": "اسم",
      "relation": "مجرور",
      "case": "مجرور",
      "explanation": "بِسْمِ: اسم مجرور بحرف الجر، وعلامة إعرابه الكسرة الظاهرة على آخره."
    }
  ]
}
```

### `POST /ask`
سؤال مبسّط عن كلمة داخل آية محددة (مطابقة نصية، وليس فهم لغة طبيعية حر).

```json
{"question": "أعرب كلمة بِسْمِ", "surah": 1, "ayah": 1}
```

## خطوات تالية لجعله "ذكاءً اصطناعيًا متكاملًا" فعلًا

1. **ربط LLM فوق الـ API**: مرِّر مخرجات `/ayah/{s}/{a}` كسياق (context)
   إلى نموذج لغوي مع `LLM_SYSTEM_PROMPT_AR.txt` كتوجيه نظام، بحيث يشرح
   بلغة حرة لكنه **مُقيَّد بالبيانات المرجعية** ولا يخترع إعرابًا.
2. **توسيع محرك القواعد**: إكمال القوالب اللغوية للأنواع الـ~95 المتبقية
   من العلاقات الإعرابية غير المغطاة تفصيليًا بعد (انظر قسم التغطية أعلاه).
3. **دعم تعدد الأوجه الإعرابية**: بعض الكلمات القرآنية لها أكثر من وجه
   إعرابي عند النحاة؛ قاعدة البيانات الحالية تعرض وجهًا مرجعيًا واحدًا لكل
   كلمة، بينما القاعدة رقم 4 في التوجيه تفترض التعامل مع تعدد الأوجه.
4. **اختبارات آلية (tests)**: إضافة مجلد `tests/` يتحقق من أن كل سورة/آية
   ترجع تحليلًا متسقًا (لا كلمات مفقودة، لا استثناءات).
5. **واجهة مستخدم** (ويب أو تطبيق) تستهلك هذا الـ API.
